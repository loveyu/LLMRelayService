# 2026-08-10

### 新增
- 后端与 rust-proxy 日志改为按天分流的 JSON 文件：TS 全局接管 `console.*`，通过 `LOG_LEVEL` / `LOG_STDOUT_LEVEL` 独立控制文件与容器输出阈值，写入 `LOG_DIR/server.log.YYYY-MM-DD`；Rust 使用 `tracing-appender` 非阻塞写入 `rust-proxy.log.YYYY-MM-DD`，不再把逐请求日志转发到容器 stdout。容器默认使用 `/app/logs`，dev tmux 使用 `.local/logs`。
- rust-proxy 路由未命中日志补充 method、path、query、model、headers 与 4 KiB body preview；`authorization` / `x-api-key` 值统一脱敏，便于排查缺失或错误 model 导致的 404。
- Console 日志详情「对话列表」支持 OpenAI Responses API（Codex CLI / ChatGPT Codex 走 `/openai/v1/responses`）请求体。
  - 在 `payload-panel.tsx` 新增 `normalizeResponsesApiInput`，把 Responses API 的 `input` 数组按 `type` 归一化成 `ChatDialogViewer` 已有的 `ChatMessage` + `ContentBlock` 词表，复用既有渲染分支：
    - `message`(user/assistant) → 文本气泡；`message`(developer/system) → system 样式气泡
    - `custom_tool_call` / `function_call` → tool_use 卡片（assistant 侧，`input` 保留字符串原样展示，如 Codex `exec` 的 JS 代码）
    - `custom_tool_call_output` / `function_call_output` → tool_result 卡片（user 侧）
    - `reasoning` → thinking 折叠块（summary 为空时显示「推理内容已加密或不支持展示」占位）
    - `additional_tools` → 不进对话列表，按 namespace 拍平后并入 Tools tab
  - 通过 `RESPONSES_ITEM_TYPES` 检测 Responses API（命中任一已知条目类型才归一化，否则保留旧的 `input` 当 messages 行为）。
- `chat-dialog-viewer.tsx`：导出 `ChatMessage`/`ContentBlock` 类型供 panel 复用；`developer` 角色按 system 样式渲染并保留标签；`formatToolInput`/`ToolUseBlock` 支持字符串 `input`（整段不截断）；`ContentBlock.input` 类型放宽为 `Record | string`。
- i18n 新增 `payload.reasoningHidden`（zh/en）。

### 修复
- 修复容器启动时 Rust 已监听、但 TS 路由配置尚未首次同步的竞态：proxy 请求现在通过同步屏障循环等待，只有配置成功加载后才继续路由，不设置超时或返回启动期错误，避免把部署切换期间携带有效 model 的请求误报为 `No route found` 404。
- 新增 `PERF_ENABLED=false` 总开关以关闭周期性能日志；Rust 子进程 stderr 以 error 级进入 TS logger，启动期 panic 与异常退出仍会写文件并保留在容器输出中。
- Codex 请求此前在「对话列表」里只显示 `[input_text]` / `(empty)` 占位（viewer 不识别 Responses API 的条目结构），归一化后可正常阅读完整对话、工具调用与结果。
- 修复使用类型强制前缀 `/anthropic/`、`/openai/` 时，**故障转移（failover）到下游上游会拼接出双段路径**导致上游 404 的问题（如 `/anthropic/v1/messages` 在首个上游 429 后故障转移到 `bigmodel-linhai-a`（`targetBaseUrl=https://open.bigmodel.cn/api/anthropic`）时被转发到 `…/api/anthropic/anthropic/v1/messages`，智谱返回 `{"error":{"message":"404 NOT_FOUND"}}`）。
  - 根因：`rust-proxy` 初始路由用剥掉前缀的 `stripped_path` 解析（正确），但 `proxy.rs` 故障转移链路（`try_add_fallbacks` → `resolve_routes_by_model` / any_model 兜底）把**原始 `pathname`**（含 `/anthropic/`）直接传给 `build_route_result`，Anthropic 类型又不剥 `/v1`，于是前缀原样拼到 `targetBaseUrl` 上。
  - 修复：在 `routing.rs` 的 `build_route_result` 入口统一 `strip_type_forced_prefix`（剥掉前导 `/openai` / `/anthropic`），无论调用方传剥好的路径还是原始 pathname 都不再双拼；any_model 兜底分支原本手搓 `RouteResult`（同样双拼前缀 + 丢 search + 不剥 `/v1`），改为复用 `build_route_result` 一并修正。新增 3 条路由单测覆盖（前缀双拼回归、`/openai/` 前缀、裸 `/v1/` 不受影响）。
  - 影响：`/anthropic/`、`/openai/` 前缀请求在首个上游 429/5xx 触发故障转移后，下游上游拿到正确 URL。TS 侧（`index.ts`）故障转移链路本就用 `lookupPathname`（已剥前缀），无此问题。
- 故障转移**不再跨 provider 类型转发**：Anthropic 请求（`/v1/messages` 或 `/anthropic/`）只会故障转移到 Anthropic 上游，OpenAI 请求同理，避免「全部上游故障时把 Anthropic 请求体转发到 OpenAI 上游」这种无效转发。
  - `proxy.rs` 用初始路由的 `upstream_type` 作为权威请求类型 `request_type`，传入 `try_add_fallbacks`；same-model / 自定义兜底 / any_model 三条兜底链路全部按 `request_type` 过滤（any_model 此前忽略类型是唯一可能跨类型的入口）。
  - 配合既有的「最后一个上游的状态码错误透传给客户端」逻辑，全部同类型上游故障时客户端拿到的是最后一个同类型上游的真实错误（如 429），而不是被跨类型转发后 OpenAI 上游返回的无关错误。
- rust-proxy 转发路径**补全故障转移日志字段**：此前 `failover_from` / `failover_chain_json` / `failover_reason` / `original_route_prefix` / `original_request_model` / `retry_attempt` 在日志页恒为空/0，看不出请求发生过故障转移。
  - `RequestLog` IPC 消息（`ipc.rs`）新增上述 6 个字段；`proxy.rs` 在请求循环里累计 `failed_route_chain` + `failover_reason`（3 个失败入口：状态码/网络错误/超时统一记录），`send_request_log` 按当前 attempt 视角计算 `failover_from`（兜底路由时记初始路由）、`retry_attempt` 等，语义对齐 TS `index.ts` 转发路径。
  - `server.ts` 的 `request_log` 处理器从 IPC 消息读取这些字段（此前硬编码 null/0），连通性测试路径（`provider_test.rs`）填默认值。
- 修复流式响应在日志详情页「响应内容缺失」的问题（SSE 响应体卡片整块空白）。
  - 根因：`payload-panel.tsx` 重构成 JSON 中心面板后，`JSON.parse(response_payload)` 对 SSE 文本流必然失败，导致 `isValidJson=false` 时 tab 栏不渲染、内容区也全部跳过，「响应体」卡片只剩标题。
  - `payload-panel.tsx`：`defaultMode` 在 `!isValidJson` 时直接落到「原始」视图；tab 栏闸门从 `isValidJson` 放宽到 `payloadText`，「原始」tab 始终可见（「结构化」tab 仍仅合法 JSON 时出现）。流式响应现在能看到完整 SSE 原文，普通请求/非流式 JSON 响应行为不变。
  - `utils.ts` `extractReadableSseText`：补 Anthropic `tool_use` 重组——按 `index` 累积 `input_json_delta` 片段，`content_block_stop` 时输出 `[Tool: 名称]` + 美化后的参数 JSON。此前纯工具调用响应（如 Claude Code 的 `TaskUpdate`）在「SSE 拼接」卡片里因没有 `text` 块而整段空白。
- 修复 codex 上传图片（或大体积 Responses 请求）时 rust-proxy 返回 **413 Payload Too Large**（`Failed to buffer the request body: length limit exceeded`）的问题。
  - 根因（两层独立限制都没放开）：① 路由层 `tower_http::limit::RequestBodyLimitLayer::new(10*1024*1024)` 硬编码 10MB；② `proxy_handler` 用 axum `Bytes` 提取器取 body，受 axum `DefaultBodyLimit`（默认仅 **2MB**）约束——这才是 "Failed to buffer the request body: length limit exceeded" 的真正出处，跟 tower-http 层是两套机制，只改一层无效。
  - 修复：引入环境变量 `RUST_PROXY_MAX_BODY_BYTES`（默认 **100MB**，parse 失败回落默认值），两层限制（`RequestBodyLimitLayer` + `DefaultBodyLimit::max`）同步抬高到该值。codex 带 base64 图 + 长 system prompt + 上下文不再被转发前拦截。生产部署按需在容器 env 调整，无需改代码。
