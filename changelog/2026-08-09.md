### 新增

  - 安全性：基于 `react-markdown` + `remark-gfm`，全程不使用 `dangerouslySetInnerHTML`、也**不**引入 `rehype-raw`，源码里的任何 HTML / `<script>` / `on*` 只按字面量当文本显示，天然防 XSS；链接沿用默认协议过滤（`javascript:` 等危险协议不生效）。
  - 实现方式：新增 `components/ui/markdown.tsx`（`MarkdownRenderer`，`components` 覆写各元素、只解构需要的 props 不透传 `node`）+ `components/ui/markdown-code-viewer.tsx`（`MarkdownCodeViewer`，复用 `json-code-viewer` 的 CodeMirror + `useIsDarkMode` 套路，`@codemirror/lang-markdown`）；`ChatDialogViewer` 新增 `TextBubble` / `MessageText` / `BubbleMenu`，把 string / array 文本两个渲染分支统一收敛进去（Markdown 模式关闭 `whitespace-pre-wrap` 让 react-markdown 自己控制换行）。新增依赖 `react-markdown` / `remark-gfm` / `@codemirror/lang-markdown`（同步更新根 `bun.lock`）。

### 修复

- **关闭日志抽屉后整页空白、需刷新（真正根因）**：`DetailView` 把 `useIsMobile()` 写在了 `if (!detail) return` 早返回**之后**，违反 Rules of Hooks。抽屉打开时 `detail` 非空 → 渲染 2 个 hook；关闭抽屉 `detail` 置空 → 走早返回 → 只渲染 1 个 hook → React 抛 `Rendered fewer hooks than expected` → 无 error boundary，整棵树卸载白屏（`<main>` 直接消失，只剩刷新能恢复）。用浏览器复现定位到该报错后，把 `useIsMobile()` 移到所有 early return 之前。前两版改 `selectedId` 的本地 state / replaceState 并非根因（保留：URL 仍静默带 `?id=`、不重渲染 App）。

- **日志页关闭抽屉后列表空白、需刷新**：上一版把 `selectedId` 改成由 hash query param（`#/logs?id=`）驱动，点选/关闭都走 `navigate` 改 `location.hash`，触发 `hashchange` → 整个 App re-render，关闭抽屉后日志列表需要刷新才回来。改回 **本地 state** 持有 `selectedId`（关闭只重渲染 LogsPage，不动列表），URL 里的 `?id=` 改用 `history.replaceState` 静默写入（不触发 hashchange、不重渲染 App）；初值仍从 `?id=` 读取，直接打开/分享 `#/logs?id=<id>` 仍能定位到该条。同步回退 `use-hash-route` / `App` 里为 id 加的路由字段。

- **连通性测试日志没有响应头**：日志页详情「响应头」对 `source_request_type=connectivity_test` 的记录一直显示「没有响应头」。根因是 `rust-proxy/src/provider_test.rs` 的连通性探测拿到上游响应后只取了 `status` / body，丢弃了 `resp.headers()`，写响应日志时硬编码 `response_headers: json!({})`（DB 核对：15 条空响应头记录全是 connectivity_test，真实转发记录都有数据）。修复：`TestOutcome` 新增 `response_headers` 字段，`handle_upstream_response` / `handle_stream_response` 在消费响应体前用新增的 `header_map_to_json(resp.headers())` 快照上游响应头（结构对齐真实转发路径 proxy.rs），`emit_response_log` 改用该快照；连接失败/超时无上游响应时仍为空对象。

- **CodeMirror 在 dev 下报 Invalid hook call**：引入 `@uiw/react-codemirror` 后，dev server（vite）把它按源码 ESM 单独解析，`react` 解析到与 app/react-dom 不同的实例，触发 `Cannot read properties of null (reading 'useRef')`。`vite.config.ts` 加 `optimizeDeps.include: ['@uiw/react-codemirror']`（预打包，复用同一份 optimized react）+ `resolve.dedupe: ['react','react-dom']`（强制 react 单例）；改后 react-dom / app / @uiw 共用同一份 `react@19.2.8` chunk。生产构建不受影响（rollup 天然去重）。

- **详情指标标签显示为 i18n key**：`detail.inputTokens` / `detail.outputTokens` 两个 key 此前在 zh/en locale 都缺失，导致详情头部的 4×2 指标格里直接显示 `detail.inputTokens` 字面量。补齐为「输入 tokens / 输出 tokens」「Input Tokens / Output Tokens」。

- **移动端详情右侧内容被裁（横向溢出、无横向滚动条）**：详情抽屉里的宽内容（长 token / 长 mono 值 / 长 URL）右侧被切掉一截，且没有横向滚动条可以拉出来看。根因是 Radix `ScrollArea` 的 Viewport 内层 div 默认 `display:table + min-width:100%`（本意配合横向 ScrollBar 做横向滚动），但本项目的 `ScrollArea` 从不渲染横向 ScrollBar，超出视口的宽内容被 Viewport 的 `overflow:hidden` 静默裁掉（实测移动端 390px 视口里内容被撑到 504px、右边裁掉 ~114px）��修复：`components/ui/scroll-area.tsx` 给 Viewport 加 `[&>div]:!block [&>div]:!w-full [&>div]:!min-w-0`（用 `!` 覆盖 Radix 内联样式），把内层强制成 block + 100% 宽 + `min-w-0`，让可换行内容回缩到视口宽度。全局生效（顺带修了 bucket-table / providers 等其他 `ScrollArea` 同类的潜在裁切）；桌面端因面板内容本就在宽度内、实测无视觉变化（`innerWidth=859` = 面板宽、`horizontalOverflow=false`）。

- **移动端对话列表工具调用卡片被长工具名顶出屏幕**：对话列表里工具调用 / 工具结果卡片（`border-l-2` 那条，头部是 `flex` 行 + `truncate` 的工具名）在遇到超长单 token 工具名（如 MCP 的 `mcp__plugin_chrome-devtools-mcp_chrome-devtools__take_screenshot`）时，卡片会被撑到 ~540px、右侧顶出 390px 视口被裁掉看不见，`truncate` 也失效。根因：卡片是对话包装列（`flex flex-col items-start` + `max-w-[85%]`）里 `align-self:start` 的子项，默认按 `max-content` 撑宽，长工具名把 `max-content` 顶大；而 `max-w-[85%]` 只钳包装列自身、钳不到子项卡片。修复：`ChatDialogViewer` 给消息包装列加 `[&>*]:min-w-0 [&>*]:max-w-full`，把每个直接子项（气泡 / 卡片）都钳制在列宽内——卡片回缩到列宽后，内层 `truncate`（`overflow:hidden` → flex 子项 `min-width:0`）正常生效、长工具名带省略号截断；短内容卡片仍按内容窄排，文本气泡（`w-full`）无视觉变化。实测移动端 `maxRight=390`、`overflowBeyondViewport=0`，工具名 `clientW:147 / scrollW:448` 正常截断。

- **密钥 / 网关超时 / 故障转移策略改动后不生效（需重启 rust-proxy）**：控制台对 API Key 的新增 / 重命名 / 删除 / 改允许模型 / 改额度，以及「网关超时」「故障转移策略」的修改，写库后没有把最新配置同步给 rust-proxy，导致这些改动要等 rust-proxy 重启（或下次 provider / alias 改动触发全量 sync 时）才生效。
  - 根因：rust-proxy 的配置只在两种情况下被刷新——bridge 重连时的初始全量 sync，以及 provider / model-alias 改动后路由处理器里显式调用的 `syncConfigToRust()`。Key / 超时 / 故障转移这三类资源的写操作（`src/console-ui.ts` 的 `/__console/api/*` 与 `src/openapi-routes.ts` 的 `/api/v1/*` 两个并行的管理面）都漏了这步，所以 rust-proxy 内存里的 `api_keys` / `timeouts` / `failover` 一直停留在旧快照。
  - 修复：给这 14 个遗漏的 mutation 处理器（每个面各 7 个：5 个 key CRUD + timeouts + failover）在写库成功后补上与 provider / alias 一致的 `syncConfigToRust().catch(() => {})`（fire-and-forget，失败不影响响应）；`syncConfigToRust` 本就是全量快照推送，一次调用即把最新 keys / timeouts / failover / providers / aliases 全部刷给 rust-proxy。验证：dev 环境实测 `POST /api/v1/keys` 后 rust-proxy 日志立即出现 `Config sync: 7 providers, 2 aliases, 1 keys`，删除后回到 `0 keys`，全程无需重启。
